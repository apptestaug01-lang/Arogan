1. Problem and goals

LoanFlow stores borrower documents (PDF, DOC/DOCX, XLS/XLSX, CSV, PNG, JPG, WEBP) in an S3-compatible vault (Backblaze B2 or Cloudflare R2). The existing batch converter writes a partial text dump to .json siblings. It is lossy, pollutes the vault namespace, and cannot guarantee recovery of the original document.

Goals

  • G1 — Zero data loss. The JSON artifact alone must preserve every meaningful byte, structure, table, image, and metadata of the original, and must prove integrity against the source object.
  • G2 — Recovery guarantee. A rebuild must be byte-identical (sha256 match) to the uploaded original for every supported format within a defined size envelope.
  • G3 — Production pipeline. Idempotent, resumable, observable, failure-isolated, and safe to run on the full existing bucket as a one-time backfill and continuously on new uploads.
  • G4 — Vault-native viewing. Analysts and borrowers open a converted .json directly in the vault: human-readable summary, raw JSON, per-page text, tables, and extracted fields — never raw base64 in the DOM.
  • G5 — No vault pollution. Derived artifacts are stored in a dedicated .loanflow/ namespace so the explorer keeps showing real documents, with an explicit toggle for JSON.
Definition of lossless used here. "Converting a document to JSON with no loss" is achieved only when the JSON is a container, not a text snapshot. It carries (a) the source's canonical semantic content with geometry and cell fidelity, (b) all embedded media and OOXML package parts, and (c) a recoverable copy of the original bytes (embedded or integrity-linked). A JSON of only rawText loses layout, tables, images, and fonts and is not lossless.

3. The fidelity contract

For each format we define what "no loss" means as explicit, testable assertions.

DimensionPDFDOCXXLSX / CSVImages
Document metadata Title, author, subject, creator, producer, creation/mod dates, PDF version, page size core.xml properties, revision, dates Sheet names, count, document properties Width, height, format, channels, space, depth, EXIF/ICC when present
Text Per page, per text-run with x,y,width,height and font Per paragraph and run with style names, list structure, ordering Per cell with type, value, display text, hyperlink OCR word boxes (x,y,w,h,conf) via Tesseract TSV
Structure Page order, page count, embedded fonts and images inventory Full OOXML parts preserved (document.xml, headers, footers, numbering, styles, media) Merged ranges, row heights, column widths, number formats, formulas No loss: original pixels retained via archive
Tables Detected row/column grids with coordinates Table rows and cells as document structure Native cell grid incl. merges N/A
Media Embedded images extracted as assets; page images for scans All word/media/* files as assets Sheet images/charts as assets Original image referenced as asset
Byte recovery Embedded base64+gzip original (within budget) OR content pointer + sha256 to the immutable source object (see §8).
Every converter ships a fidelity test: rebuild the document from the archive and assert sha256(rebuild) === source.sha256. This is the only objective definition of "no data loss" that matters in production.

4. Reference architecture

One design principle: the JSON archive is a self-describing container, the original object stays immutable, and everything derived lives under a hidden .loanflow/ prefix.

1. Source of truth

The original object never moves and is never rewritten. Its ETag and a computed sha256 become the archive's identity.

2. Derived namespace

.loanflow/{docId}/document.json plus .loanflow/{docId}/assets/…. The vault explorer filters this prefix out of normal listings.

3. Async workers

An idempotent queue drives conversion. Workers are stateless, retried with backoff, and write results transactionally to S3 and Postgres.

Why a queue instead of doing this inside the upload request?

  • Conversion of a 50-page scanned PDF takes seconds to minutes — too slow for a request lifecycle.
  • The upload path should return fast and never fail because a converter crashed.
  • Backfill of an existing bucket is just "enqueue every object", reusing the same workers.
  • Failures isolate per document; a poison message does not take down uploads or reads.

KeyOwnerContentLifecycle
borrowers/…/documents/{documentId}/… Borrower upload Original immutable file Kept forever; deletion only via documented soft-delete flow

.loanflow/{documentId}/assets/* Worker Page images, media files, thumbnails Rebuildable; candidate for Infrequent-Access tier

Why .loanflow/ at the bucket root and not a sibling .json? Sibling JSON in the same folder breaks the explorer contract (folders contain only real documents), breaks the documents/{docId}/{file} 1:1 invariant, and mixes content types. A hidden dot-prefix namespace keeps listings clean while remaining inside the same bucket for cheap reads. Prefix isolation still applies: borrowers can only reach their own borrowers/{userId}/…; the derived namespace is keyed by documentId and served only through authorized APIs.

6. DocumentArchive JSON schema

A versioned container. Every section is optional-with-purpose: an empty section must never silently mean "data missing" — the schema is explicit about what was and was not captured.

{
  "schemaVersion": "1.0",
  "archiveType": "document-archive",
  "id": "documentId-here",

  // (a) Provenance + integrity of the SOURCE object
  "source": {
    "key": "borrowers/u/apps/a/documents/d/loan.pdf",
    "contentType": "application/pdf",
    "size": 1048576,
    "etag": "9a7...",
    "sha256": "e3b0c442...",
    "originalName": "loan.pdf",
    "uploadedAt": "2026-09-05T03:00:00Z"
  },

  // (b) Converter provenance
  "generatedBy": { "tool": "loanflow-archiver", "version": "1.0.0", "at": "2026-09-05T03:01:00Z" },

  // (c) The converter's own claim about fidelity
  "fidelity": {
    "roundTripVerified": true,          // rebuild + sha256 === source.sha256
    "originalAvailable": "embedded",    // embedded | gz-object | source-object
    "warnings": []                        // e.g. ["password-protected xlsx", "ocr fallback"]
  },

  // (d) Format-specific deep structure (lossless target)
  "format": "pdf",                      // pdf | docx | xlsx | image | csv | unknown
  "metadata": { /* format-specific, see s7 */ },
  "pages": [
    {
      "pageNumber": 1,
      "width": 595.28, "height": 841.89,
      "blocks": [
        { "kind": "text", "bbox": [72, 72, 250, 14],
          "runs": [{ "text": "Income Statement", "font": "Helvetica-Bold", "size": 16, "color": "#000000" }] },
        { "kind": "table", "bbox": [...], "grid": [ {"cell": ["Date", "Amount"]} ] },
        { "kind": "image", "asset": ".loanflow/d/assets/media-0001.png", "bbox": [...] }
      ],
      "ocr": { "words": [{ "text": "Statement", "bbox": [...], "conf": 0.94 }], "text": "..." }
    }
  ],
  "text": { "rawText": "...", "charCount": 12345, "searchable": true },

  // (e) Assets referenced above (embedded or object refs)
  "assets": [
    { "name": "media-0001.png", "key": ".loanflow/d/assets/media-0001.png", "sha256": "...", "size": 2048 }
  ],

  // (f) Byte archive (optional, see s8)
  "byteArchive": {
    "encoding": "base64", "compression": "gzip",
    "rawSize": 1048576, "archiveSize": 351234,
    "data": "H4sIA..."  // present only when policy = embed
  },

  // (g) Reuse existing field layer for autofill/search
  "classification": { "documentType": "BANK_STATEMENT", "confidence": 0.9 },
  "fields": { "accountNumber": { "value": "...", "confidence": 0.93, "source": "hybrid", "page": 1 } }
}

Design rules

  • Versioned schema — schemaVersion gates all readers; consumers must reject unknown versions.
  • Every structure carries geometry — text without coordinates is not lossless for layout-sensitive documents (bank statements, balance sheets).
  • Cells carry types — XLSX must not reduce everything to display strings; keep type: number|string|date|bool|formula|error.
  • Assets are referenced, not inlined into pages — keeps the container readable and lets the viewer stream assets lazily.
  • Fields are a view, not the content — autofill fields remain in a separate top-level object so deleting them never destroys document content.

7. Per-format converters

Concrete tooling and capture strategy for each format. All converters share one interface:

interface ArchiveConverter {
  supports(contentType: string): boolean;
  convert(ctx: ConvertContext): Promise<ArchiveBuild>;
}

PDF — text layer + geometry + raster fallback + OCR

  • Primary: use pdfjs-dist (already a frontend dependency; add to backend) to read text items with transform matrix [x, y, w, h], font name and size per run. Extract page dimensions and document metadata.
  • Embedded media: iterate PDF image XObjects, save each to assets/media-*.png/jpg.
  • Scanned fallback: if a page's text length < threshold, rasterize with pdftoppm -r 300 (already used in pdfToImageConverter.ts) and OCR with Tesseract TSV to keep word boxes and confidence.
  • Fix the existing bug: never send a PDF path into sharp(); use pdftoppm (poppler) as in the extraction pipeline.

DOCX — OOXML package fidelity + HTML render

  • Unzip the package (use adm-zip, already a dependency) and capture: word/document.xml, headers, footers, numbering, styles, core properties, and all word/media/*.
  • Extract the content stream into ordered block objects (paragraphs, runs, tables, images) instead of one undifferentiated string.
  • Keep Mammoth convertToHtml output in a parallel html field for fast rendering, but the canonical content is the structured blocks.
  • Media bytes are stored as assets with their original relationship IDs so the DOCX can be reconstructed.

XLSX / XLS / CSV — cell-faithful grid

  • Use xlsx with cellFormula: true, cellNF: true, cellStyles: true, cellDates: true.
  • Serialize each sheet as an array of rows of typed cells: { t: "n|s|d|b|e|z", v, w, f?, z?, c? } where c is an optional comment.
  • Capture !merges, !cols, !rows, and page setup so the visual grid is reproducible.
  • Store formula text (f) so calculations are not frozen into values; the viewer can show both f and cached v.
  • CSV is plain text: read with a strict parser (csv-parse or papaparse style) that preserves quoting and line endings.

Images — full metadata + word-level OCR

  • Capture sharp metadata: width, height, format, channels, space, depth, and (when available) EXIF/ICC profile presence.
  • OCR with Tesseract TSV so each word carries a box and confidence (improves on the current line-joined dump).
  • Pre-process with adaptive thresholding rather than a fixed threshold(128) to preserve low-contrast scans.
  • The image itself remains the source; the JSON adds a searchable text layer and geometry.

8. Embed vs reference: how "no loss" is guaranteed at scale

A JSON file that embeds a 2 GB PDF as base64 is not a document archive, it is a worse object store. The guarantee comes from policy, not from forcing bytes into JSON.

Source sizeStrategyLossless guarantee
≤ 25 MB (typical bank statement, PAN, ITR, most scans) byteArchive.data = base64 of gzipped original bytes, embedded in document.json document.json alone can rebuild a byte-identical original
25 MB – 100 MB Original stays as the immutable source object; .loanflow/.../original.gz holds a gzipped copy; byteArchive records sha256, sizes, and pointer Full bytes are in two independent locations; JSON + any one copy rebuilds the original
> 100 MB (multipart ceiling up to 5 GB) Original object is the byte store; JSON carries full semantic content + integrity pointer Semantic losslessness (every readable datum) + verifiable integrity; raw bytes live in S3
Recommended production default: embed up to 25 MB (gzip usually shrinks PDFs/DOCX/XLSX by 40–80%, so the payload stays modest), use the original.gz object tier to 100 MB, and rely on the source object above that. Store the policy in config so operators can raise the embed threshold later. Every archive, at every tier, records source.sha256 and fidelity.roundTripVerified, which is the actual guarantee auditors care about.

Gzip before base64 — expected sizes

SourceRawGzip approx.base64 of gzip

9. Worker pipeline and state machine

stateDiagram-v2
    [*] --> PENDING: upload complete event
    PENDING --> PROCESSING: worker leases job
    PROCESSING --> COMPLETED: archive verified sha256
    PROCESSING --> FAILED: converter error
    PROCESSING --> RETRYABLE: transient error (timeout/5xx)
    RETRYABLE --> PROCESSING: backoff + retry
    RETRYABLE --> DEAD_LETTER: max attempts
    FAILED --> PENDING: operator re-enqueue
    DEAD_LETTER --> [*]
    COMPLETED --> [*]

Worker behaviour

  1. Idempotency key. Every job is addressed by documentId. Before converting, read the existing DocumentArchive row; if status = COMPLETED and the converter version is unchanged and source.sha256 matches the object's current checksum, skip.

  2. Download with integrity. Stream the object to a temp file (or cap the in-memory buffer at the tier threshold). Compute sha256 and compare to object metadata when present. Refuse to archive a source whose checksum cannot be verified.

  3. Convert under a wall-clock budget. Wrap per-document conversion in a timeout (e.g. 90 s for ≤10 MB, longer for larger tiers) so a pathological file cannot stall the queue.

  4. Write assets first, then the archive. Assets go to .loanflow/{docId}/assets/…, then document.json is written last with metadata referencing the assets. A crash before the final write leaves only orphaned assets, which a sweeper removes.

  5. Verify then commit. Optional but recommended for the embed tier: rebuild from the archive in a sandbox and compare sha256 before marking COMPLETED.

  6. Update Postgres transactionally. Upsert DocumentArchive status, timings, converter version, asset list, fidelity result.

Failure isolation and retries

Failure classExamplePolicy
TransientS3 5xx, network drop, timeoutRetry with exponential backoff + jitter, max 5 attempts
PermanentCorrupt file, unsupported variant, password-protectedMark FAILED with a structured error and warnings; never block the queue
PoisonSame document fails repeatedlyMove to DEAD_LETTER after max attempts; alert on-call
OperatorConverter version improvedRe-enqueue or run backfill by converterVersion < X

Queue options for this stack

Recommended: BullMQ backed by the existing Redis/Postgres deployment, or SQS if the team moves off Render free-tier. On Render, a single Node worker process with p-queue concurrency (like the current MAX_CONCURRENCY pattern) is acceptable to start, then graduate to BullMQ/SQS when multi-instance.

Concurrency and memory

Cap concurrency at workers × 2 and track RSS. Each 25 MB embed job needs ~3–4× that in transient memory (source buffer, gzip, base64). At 4 workers, budget ~400 MB for the worker. Never load a >100 MB source fully into memory — stream to disk first.

10. Database schema evolution

Postgres tracks status and serves the API; the JSON payload itself lives in S3 and is fetched on demand. This mirrors the existing Document / DocumentExtraction split.

model DocumentArchive {
  id               String   @id @default(cuid())
  documentId       String   @unique   // FK to Document.id
  document         Document @relation(fields: [documentId], references: [id], onDelete: Cascade)

  status           String   @default("PENDING")  // PENDING|PROCESSING|COMPLETED|FAILED
  schemaVersion    String?
  converterVersion String?
  archiveKey       String?  // .loanflow/{docId}/document.json
  sourceSha256     String?
  sourceEtag       String?
  sourceSize       Int?
  byteTier         String?  // embedded | gz-object | source-object
  fidelityVerified Boolean  @default(false)
  error            Json?
  warnings         Json?
  assets           Json?    // [{name,key,sha256,size}]
  startedAt        DateTime?
  completedAt      DateTime?
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt

  @@index([status])
  @@index([documentId])
}
  • Keep DocumentExtraction untouched: it is the autofill/field layer. The archive is a superset; fields in the archive JSON can be populated from it after conversion.
  • Add a derivedAt/converterVersion gate so a newer converter can detect stale archives during backfill.
  • A scheduled sweeper (extend cleanup.service.ts) removes orphaned .loanflow/ assets whose DocumentArchive row is not COMPLETED and older than a threshold.

11. In-vault JSON viewing and opening

The vault already renders .json keys as pretty-printed text (DocumentVaultView.tsx, handleFileOpen JSON branch). We extend that into a proper JSON archive viewer without ever dumping raw base64 into the DOM.

Explorer integration

  • Hide derived objects by default. listExplorer (explorer.service.ts) should skip the .loanflow/ prefix at the bucket root, and skip nothing inside real document folders (they no longer contain JSON siblings).
  • Show JSON as a property, not a file. Each real document row gets a "JSON" action button when a COMPLETED DocumentArchive exists. Clicking it opens the archive viewer for that documentId — no fake file entry, no content-type guessing.
  • Fix the key-viewer bug. getKeyView hardcodes contentType: 'application/json'; change it to headObject's real content type so opening a PDF by key does not render the JSON branch.

Viewer UX (build on the existing modal)

Summary tab

File name, size, sha256, converter version, fidelity badge (verified/failed), classification, and extracted fields in a table — sourced from the archive header, not a re-parse.

Content tab

Pages/sheets rendered from pages/data: text blocks, tables as real HTML tables, sheet grids with type badges, images loaded lazily from asset URLs.

Raw JSON tab

Large-file-safe viewer: fetch is capped and paginated, text rendered into a <pre> via textContent, with find-in-document. A "Download .json" button streams the object through a presigned URL.

Hardening the JSON render path

  • Never use dangerouslySetInnerHTML for archive content — the current <pre> + JSON.stringify(parsed, null, 2) approach is safe; a tree viewer must set textContent.
  • Size cap on the raw view: if archiveSize > ~10 MB, show summary/content first and stream the raw JSON in chunks or hand the download URL directly to the browser.
  • Lazy assets: media and page images render only when their tab is active, using short-lived presigned URLs (5 min, consistent with PRESIGNED_DOWNLOAD_TTL_SECONDS).
  • Error states: show fidelity.warnings prominently (e.g. "password-protected sheet — content may be partial").

12. Security

ThreatControl
Direct access to derived objects Bucket stays private; every read is a presigned URL issued only after tenant-prefix authorization (reuse the existing startsWith(borrowers/{userId}/) and doc.userId === userId checks in explorer/viewer services).
Zip-slip / path traversal in converters DOCX/XLSX are zip packages: validate every entry name against the package root, strip absolute paths and .., and never write extracted parts outside the temp sandbox.
XXE / XML attacks in OOXML Parse package XML with an entity-expansion-safe parser (disable DTD/external entities). Mammoth and xlsx already ignore DTDs, but any raw document.xml parsing must not use DOMParser defaults that resolve entities.
Huge or deeply nested JSON on read Read with a streaming JSON parser for large files; enforce a max archive size and max nesting depth in the viewer.
XSS via document text All document-derived text is rendered as text nodes only. No HTML injection path in any viewer tab.
Secrets in metadata Sanitize metadata: never store credentials or URLs from document properties; redact before persisting if detected.
Poison PDF / image bombs Workers run with OS-level memory cap; conversion timeout; pixel-dimension and decompression-size guards before OCR/rasterization.
Borrower sees another's JSON Archive is keyed by documentId which is owned by the user; API always resolves via prisma.document with a userId filter before issuing URLs (mirror getDocumentView).

14. Backfill and rollout

The same code path that archives new uploads archives the existing bucket. No separate one-off script diverges from the pipeline.

  1. Phase 0 — freeze converter semantics. Define schema v1, converter interface, fidelity contract, and fixtures. Merge the worker behind a feature flag.

  2. Phase 1 — dry-run backfill. List all source objects (paginate ListObjectsV2), compute sha256, and report what would be archived, tiered by size, without writing. Produce a dashboard count.

  3. Phase 2 — rate-limited backfill on staging. Enqueue in batches (e.g. 500 at a time), run workers at low concurrency, compare archive counts and fidelity failure rate against the dry-run numbers.

  4. Phase 3 — production backfill. Resume-safe: jobs are idempotent by documentId; restart mid-run simply skips completed archives. Monitor failure rate and dead-letter count.

  5. Phase 4 — continuous mode. Hook the worker to the upload-complete event so every new document is archived. Keep a scheduled reconciler that finds source objects with no COMPLETED archive older than X minutes (self-healing if an event is lost).

  6. Phase 5 — enable the vault toggle. Ship the archive summary endpoint, the viewer tabs, and the explorer "JSON" action; then turn off the old sibling-.json writer and remove those files.

Cleanup note. Removing legacy sibling .json files is a delete operation: confirm the inventory first, run in dry-run, and follow the repo's delete policy before executing any removal.

18. Corner-case register

Edge cases the chunk plan must design for, grouped by where they bite. Each row names the condition, why it is a real risk in this codebase, and which chunk owns the mitigation. Treat every row below as a required test case, not a nice-to-have.

Two findings change the plan's assumptions: (1) headObject() (storage.service.ts:205) stores the S3 ETag as checksum — for multipart uploads an ETag is not the file hash, so "verify sha256 against DB checksum" is only valid for single-PUT objects; the archive worker must compute its own sha256 from the bytes it downloads. (2) DocumentVaultView.tsx runs JSON.parse on whatever it opens, so a large embedded archive would freeze the tab — the viewer must never parse a full archive for the summary tab.

A. Upload and integrity

#Corner caseWhy it is real hereMitigation owner
A1 Multipart ETag is not a content hash Objects >100 MB go through multipart.service.ts; B2 returns an ETag of md5(part1..partN)-N, not the file digest. DB checksum cannot prove integrity. C3/C4: always compute sha256 on downloaded bytes; treat stored checksum as advisory only; for the source-object tier record ETag + size and mark integrity as "object-preserved, content unverified".
A2 Upload completed but object vanished completeDocument does headObject then returns 201; a lifecycle rule or external deletion could remove the object afterwards. C4/C5: worker re-heads before download; on 404 mark FAILED with code SOURCE_MISSING and do not retry blindly (reconciler decides).
A3 Duplicate uploads of the same logical file A borrower may upload the same PDF for two applications, creating two documentIds with identical bytes. C4: optional content-addressed dedupe — if a COMPLETED archive exists for the same sha256, reuse it by reference instead of storing a second embedded copy.
A4 Object overwritten by key reuse Keys embed documentId so collisions are unlikely, but sanitizeFileName can map two names to one key. C0/C4: keep documentId in the key (already true); archive worker compares current ETag/size to the row before reusing a cached archive.
A5 Zero-byte or whitespace-only file passes upload Presign validates contentLength > 0 but a 1-byte PDF or empty CSV is accepted; converters must not hang or produce empty archives. C2: return a valid archive with an explicit fidelity.warnings = ["empty-content"], not a throw.

B. Converter and fidelity

#Corner caseWhy it is real hereMitigation owner
B1 Content type lies (extension vs bytes) ALLOWED_DOCUMENT_CONTENT_TYPES is client-supplied at presign; a renamed file can be application/pdf with PNG bytes. C2: sniff magic bytes first; fall back to the declared type only for ambiguous cases; record both in metadata.detected.
B2 Encrypted / password-protected files Encrypted PDFs, DOCX (agile encryption), and XLSX are common in loan files; parsers may return garbage or throw. C2: detect encryption markers; store a minimal archive with warnings=["encrypted"] and rely on the byte tier so no data is lost even though text extraction is empty.
B3 PDF page rotation and crop boxes pdfjs-dist transforms are in PDF space; /Rotate 90 or crop boxes shift coordinates. Naive bbox storage becomes wrong. C2: normalize coordinates per page using viewport (scale + rotate) before writing blocks.
B4 Mixed text + scanned PDF A 20-page statement may have 15 born-digital pages and 5 scans. Whole-document OCR fallback (as today) is wasteful and error-prone. C2: decide OCR per page (text length threshold), rasterize only empty pages, store per-page OCR plus page-image assets.
B5 OCR binary or language data missing at runtime tesseract and eng.traineddata must exist in the runtime image (backend Dockerfile adds them, but local dev or slim images may not). C2/C5: capability probe at worker start; graceful degradation to warnings=["ocr-unavailable"] with no crash.
B6 Non-Latin / multi-column PDF text order Devanagari, tables, and two-column layouts can interleave text runs in extraction order, corrupting reading order. C2: sort runs by (y, x) clusters and keep raw run list; do not claim paragraph order when geometry is ambiguous; note in fidelity warnings.
B7 XLSX cell precision and date loss Excel stores numbers as IEEE double; long account numbers (16+ digits) and dates need exact serial + display text. xlsx with cellDates may shift timezones. C2: keep t (type), v (raw), w (formatted text), and z (number format); never rely on re-serializing JS dates; preserve raw cell strings for identifiers.
B8 Formulas and cached values xlsx returns f (formula) and cached v; some writers omit cached results, making cells appear empty. C2: store f and v independently; viewer shows formula when value is absent; do not flag missing cache as empty cell.
B9 CSV encoding and delimiters UTF-8 BOM, Windows-1252 exports, and semicolon-delimited regional CSVs defeat naive split(','). C2: strict CSV parser with BOM strip, encoding detection, and delimiter sniffing; preserve the raw line data.
B10 Legacy DOC and XLS binary formats application/msword and application/vnd.ms-excel are allowed; mammoth handles DOCX only and xlsx handles BIFF8, not older or RTF masquerading as DOC. C2: attempt binary parse; on failure store bytes + warnings=["legacy-format-unparsed"] rather than a false "empty" archive; round-trip still holds via byte tier.
B11 OOXML zip-slip and entity expansion DOCX/XLSX are zips; crafted entries (../) or DTDs could read files or expand entities when unpacking parts. C2: validate every zip entry name; reject DTD/external entities; extract only known parts to a sandbox path.
B12 Very large page/image counts and memory spikes A 500-page scan at 300 DPI can exhaust memory if rasterized eagerly. The existing pipeline caps at 10 MB and 25 s. C2/C5: per-page budget and streaming; rasterize one page at a time; overall archive timeout with partial-result persistence.

Bottom line. True lossless JSON conversion is a three-part deliverable: (1) a fidelity contract and versioned DocumentArchive schema, (2) per-format converters that preserve structure and geometry and record integrity, and (3) an idempotent worker pipeline that writes derived objects to a hidden namespace. Paired with the vault JSON viewer (summary, content, raw tabs), this gives LoanFlow a searchable, openable, verifiable JSON copy of every vault document with zero information loss — and the existing extraction/autofill layer rides on top unchanged.
