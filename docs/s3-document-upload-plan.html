4. Security model — per-customer isolation

  • Bucket/store: block all public access; no public objects.
  • Key structure: tenants/{tenantId}/applications/{applicationId}/documents/{docId}/{uuid}-{filename} — tenantId enforced server-side, never trusted from client.
  • Least privilege: one app identity with s3:PutObject / s3:GetObject scoped to bucket + s3:prefix; never s3:*.
  • Pre-signed URLs: exact key + exact op + short TTL (upload ~15 min, download ~5 min); constrain Content-Type & Content-Length on PUT.
  • Encryption at rest: SSE-KMS or SSE-S3 (MinIO supports SSE).
  • Authorization + audit: every list/get verifies caller owns tenantId/applicationId; log upload/download/delete to AuditLog.
  • Malware / validation: size + type allow-list; post-upload virus scan (ClamAV) before marking Verified.
  • Immutability: versioning + Object Lock to prevent tampering / accidental deletes.

  • Storage: MinIO container on your own host — identical S3 API, no bill.
  • Compute: Node backend + MinIO as containers; no Lambda/AWS billing.
  • Intelligence: local Ollama (open weights) for structuring; rule-based as the free baseline.
  • DB: self-hosted Postgres (already in stack) or SQLite for zero infra.
Honest caveat: "free" assumes you provide the host (laptop / spare server / free-tier VPS). For truly zero-hardware you'd need a cloud free tier (R2/AWS) — not permanent $0. MinIO-on-your-own-host is the pure $0 path.

1

Secure, signed uploads Req 1

The browser must never hold MinIO credentials. The server mints a short-lived, single-object, single-operation presigned URL.

Deep-dive decisions

  • Key is server-built: tenants/{tenantId}/applications/{applicationId}/documents/{docId}/{uuid}-{filename}. tenantId/applicationId come from the authenticated session, not the request body.
  • Presign endpoint: POST /api/documents/presign → returns the PUT URL + required Content-Type/x-amz-meta-* fields. Gated by authMiddleware.
  • Binding policy (the security core): TTL ≈ 15 min; Content-Type constrained to an allow-list (pdf, png, jpg, docx, xlsx…); Content-Length capped (e.g. 5 GB); server-computed checksum must match on complete.
  • Bucket posture: BlockPublicAccess = ALL; no public ACL; a bucket policy that denies everything except via a presigned URL issued by the app role (least privilege: s3:PutObject/s3:GetObject only, never s3:*).
  • CORS: locked to the app origin + PUT/GET + the exact allowed headers — no *.
Browser ──auth─▶ POST /presign (server builds key, checks tenant) ──▶ presigned PUT URL (TTL 15m, CT+size bound) └──PUT file直▶ MinIO (rejects if CT/size/checksum mismatch) Server then writes Document metadata + AuditLog (upload_initiated→completed)
Why presigned PUT (not presigned POST): PUT gives a single, tamper-evident object contract and clean checksum validation; POST is fine for simple forms but weaker on content-type/length guarantees at scale.
2

Large-file pipeline > 100 MB Req 2

A single PUT is fragile for big files (memory, timeout, no resume). For >100 MB we use S3 multipart upload, which MinIO supports natively and which the AWS SDK v3 drives unchanged.

Deep-dive decisions

  • Flow: POST /api/documents/presign-multipart (size, name, category) → server calls CreateMultipartUpload and returns the uploadId + one presigned UploadPart URL per part.
  • Client: slices the file into parts (8–64 MB; 10 MB is a safe default). A 100 MB file → ~10 parts; 250 MB → ~25 parts. Each part is PUT to its presigned URL; ETag + part number are collected.
  • Finalize: POST /api/documents/complete-multipart (uploadId + parts[]) → server calls CompleteMultipartUpload, then writes Document + audit.
  • Resume / abort: the server keeps an upload session (uploadId + received part ETags) keyed by a client token; on failure the client re-requests missing parts (resume) or calls AbortMultipartUpload (cancel). Parts already uploaded are not re-sent.
  • Concurrency & limits: 4–5 parallel part uploads; respect the 10,000-part ceiling (pick part size so size / partSize ≤ 10000); show real progress per part.
  • Cleanup: a lifecycle rule aborts incomplete multipart uploads after 7 days so orphaned parts don't accrue.
Acceptance for this chunk: a 250 MB PDF uploads with live progress, survives a paused/resumed network drop by re-sending only missing parts, and lands as one valid object in MinIO.
3

Metadata, lifecycle & audit backend

Bytes stay in MinIO; the database tracks where they are and who owns them.

  • Document model: id, tenantId, applicationId, category (the 7 canonical folders from §1), s3Key, originalName, size, checksum, contentType, status (PENDING→UPLOADED→VERIFIED), uploadedBy, createdAt.
  • Routes: presign, presign-multipart, complete-multipart, GET / (scoped list), GET /:id/view (presigned download), DELETE /:id (soft-delete + object delete), POST /:id/link (attach to form).
  • Audit: every presign, complete, view, link, delete writes an AuditLog row with tenantId, actor, and object key. Cross-tenant key access attempts are rejected and alerted.
  • Status: starts UPLOADED (readable now); moves to VERIFIED only after the optional ClamAV scan in Chunk 6.
4

Explorer view of the store Req 3

Users browse the bucket like a file manager, but the listing is always tenant-scoped and server-enforced.

Deep-dive decisions

  • Backend listing: ListObjectsV2 with prefix = tenants/{tenantId}/ and delimiter = '/'. CommonPrefixes → folders; Contents → files (with size, lastModified, key). Pagination via ContinuationToken.
  • Tree shape: root → application folders → the 7 categories → documents. The 7 canonical folders from §1 become the first-level categories so the UI matches the business taxonomy.
  • Frontend DocumentExplorer: breadcrumb, folder grid, file list with sort/search (server-side prefix filter), pagination. It reuses the existing mock DocumentVaultView as its visual base and swaps mock data for the real list API.
  • Click-to-open: selecting a file calls Chunk 5's viewer — the explorer never exposes raw keys to the user, only display metadata.
GET /api/documents/explorer?prefix=…&continuation=… └─▶ ListObjectsV2 (tenant prefix + "/") ──▶ { folders:[…], files:[{key,size,modified}], nextToken } └─▶ DocumentExplorer renders tree; clicking a file ──▶ Chunk 5 viewer
5

Readable viewer + link-to-form Req 4 · $0

Every uploaded file must be openable in-app and attachable to a loan form — with zero runtime cost: the browser fetches straight from MinIO, no server proxy, no paid OCR.

Deep-dive decisions

  • Read: GET /api/documents/:id/view returns a presigned GET URL (TTL ≈ 5 min). The browser opens it directly — PDFs via pdfjs-dist, images via <img>, others via download. No bytes ever touch the app server.
  • Viewer component DocumentViewer: streaming render, page nav for PDFs, filename/size/status header. Reuses pdfjs-dist already chosen in §5.
  • Link-to-form: each form section gets an "Attach from Vault" button → opens VaultPicker (Chunk 4 explorer in picker mode) → user selects a doc → POST /api/documents/:id/link { formId, field }. This sets the document's applicationId/link row. The form renders a document chip that opens the viewer.
  • $0 guarantee: for now the file is only read and linked — no extraction pipeline runs, so there is no compute or API cost. Structured-data capture is explicitly deferred to §5/§7 Chunk 4.
Why this is safe to ship first: it delivers immediate business value (upload big secured files, browse them, open them, attach them to forms) on the free stack, while the costly intelligence layer stays optional and isolated.
6

Enterprise hardening optional

Production-grade guards layered on after the module works.

  • Encryption at rest: SSE-S3 (or SSE-KMS if you later move to AWS) on the bucket.
  • Immutability: versioning + Object Lock (WORM) so a verified document can't be silently overwritten or deleted — important for loan/compliance records.
  • Malware: ClamAV scan on complete-multipart before status flips to VERIFIED; quarantine on hit.
  • Resilience: rate-limit presign per tenant; 7-day abort rule for incomplete multipart; alert on any cross-tenant access attempt.
  • Observability: metrics on upload size/distribution, presign volume, and failed parts.
Build order: Chunk 0 → 1 (secure single-file upload) → 3 (metadata) → 4 (explorer) → 5 (viewer + link) gives a usable $0 product. Chunk 2 (>100 MB multipart) and Chunk 6 (hardening) are independent follow-ons. No code has been written yet — this section is the implementation contract for the Document Vault Module.
